```text
==================================================

The Customer should be able to:

1. CUSTOMER PROFILE
- View own profile
- Update own profile
- View own basic account information

2. VEHICLE DISCOVERY
Customer should be able to:
- View available vehicles
- Search vehicles by city
- Filter vehicles
- View vehicle details

Vehicle search is CITY BASED.

Example:
Customer selects Mumbai → show eligible Mumbai vehicles.
Customer selects Pune → show eligible Pune vehicles.

Vehicle location and Customer location are not GPS based.

Customer should be able to see:
- Vehicle brand
- Vehicle model
- Vehicle type
- Seating capacity
- Fuel type
- AC / Non-AC
- Price per KM
- Vehicle features
- Vehicle images
- Vehicle city
- Availability

Customer must NOT see private administrative/verification documents such as:
- RC documents
- Driver license documents
- Other admin-only documents

Only vehicles satisfying the required business rules should be shown.

A vehicle should be considered available only when appropriate approval, active status and booking-conflict rules are satisfied.

3. BOOKING REQUEST

Customer should be able to create a booking request.

Booking request may contain:
- Vehicle
- Pickup city
- Pickup address
- Drop location
- Pickup date
- Pickup time
- Return date if applicable
- Number of passengers
- Trip type
- AC / Non-AC preference
- Customer mobile number
- Additional trip details

Trip types:
- LOCAL
- OUTSTATION

"ALL" is only a search/filter option, not a booking trip type.

IMPORTANT:
Pickup city must match the selected vehicle's operating city.

Example:
Vehicle city = Mumbai
Pickup city = Mumbai → allowed
Pickup city = Pune → not allowed

4. PRICING

Vehicle search displays the vehicle's rate per KM.

However, this displayed rate is NOT necessarily the final rental amount.

After the booking request:
Customer and Owner communicate and decide the final rental price.

The platform should store the final agreed amount.

Customer-to-Owner rental payment is OUTSIDE the platform.

Do not implement payment gateway unless an existing payment system already exists.

5. BOOKING FLOW

Expected booking flow:

Customer submits booking request
        ↓
PENDING
        ↓
Owner reviews request
        ↓
Owner communicates with Customer
        ↓
Final price/details agreed
        ↓
Owner ACCEPTS or REJECTS
        ↓
If rejected → rejection reason required
        ↓
If accepted → Driver assignment
        ↓
Driver assigned
        ↓
Booking becomes CONFIRMED

Customer should be able to see appropriate booking statuses.

6. DRIVER INFORMATION

After booking confirmation / Driver assignment, Customer should be able to see appropriate Driver details such as:
- Driver name
- Driver mobile number
- Driver details required for the confirmed trip

Customer must NOT see private Driver verification documents.

If Owner changes the Driver after confirmation:
- New Driver details should be updated
- Customer should receive notification
- Trip/booking history must remain consistent

7. VEHICLE REPLACEMENT

If the confirmed vehicle becomes unavailable:
- Owner communicates with Customer
- Replacement decision is made
- Customer receives updated vehicle information/notification

Customer should see the latest confirmed vehicle information.

8. TRIP

Customer should be able to view:
- Upcoming trips
- Confirmed trips
- Ongoing trips
- Completed trips
- Trip history

Trip start is performed by Driver using OTP verification.

Customer should not start/end the trip.

9. CANCELLATION

Owner cancellation is definitely supported.

Customer cancellation is NOT finalized as a business rule yet.

However, prepare the backend architecture/API so a Customer cancellation endpoint can exist without hardcoding a final cancellation policy.

Do NOT invent cancellation penalties or rules.

Use a configurable/extendable design and clearly mark policy-dependent logic as TBD.

10. NOTIFICATIONS

Customer should receive notifications for important events such as:
- Booking request submitted
- Booking accepted
- Booking rejected + reason
- Booking confirmed
- Driver assigned
- Driver changed
- Vehicle changed
- Trip updates
- Trip started/completed
- Cancellation/update notifications where applicable

11. SECURITY

Customer APIs must be protected using the existing JWT/Spring Security architecture.

Do NOT create a second authentication system.

Use the existing authenticated user identity from the SecurityContext/JWT.

Do NOT trust customerId directly from request body when it can be obtained from the authenticated user.

Example principle:

Authenticated JWT
      ↓
SecurityContext
      ↓
Current User
      ↓
Customer Profile
      ↓
Customer-owned resources

Customer must only access:
- Their own profile
- Their own bookings
- Their own trips
- Their own notifications

Customer must NOT access another customer's booking/trip data by changing an ID in the URL.

12. API DESIGN

Before coding, identify all required APIs.

For each API specify:
- HTTP method
- URL
- Authentication requirement
- Required role
- Request DTO
- Response DTO
- Validation
- Service method
- Repository queries
- Business rules
- Possible exceptions
- HTTP response status

13. DTOs

Follow the existing project DTO convention.

Prefer separate:
- Request DTO
- Response DTO

Do not expose entities directly from controllers.

Use the existing MapStruct configuration if already present.

14. DATABASE

Before modifying the database:
- Inspect existing entities and relationships
- Identify which existing tables can be reused
- Identify missing fields
- Identify missing relationships
- Identify whether Customer profile already exists
- Identify how Booking and Trip are currently modeled

Do NOT create duplicate tables for concepts that already exist.

15. BUSINESS RULES

Important rules:

- Customer can search vehicles by city.
- Customer cannot see unapproved vehicles.
- Customer cannot see unavailable/conflicting vehicles.
- Customer cannot book another Customer's booking.
- Customer cannot modify Owner/Driver data.
- Customer cannot assign Driver.
- Customer cannot approve Vehicle/Driver.
- Customer cannot start/end trip.
- Customer can only access their own booking/trip history.
- Final rental amount is agreed between Customer and Owner.
- Rental payment is outside the platform.
- Driver is a global platform resource and is NOT permanently owned by one Owner.
- Any eligible Driver may be used by any Owner.
- Driver's location is only used as current-location information/filtering and is NOT an ownership restriction.
- Customer does not get live Driver tracking.
- No rating/review functionality is required currently.
```

# CAR RENTAL APPLICATION
## Software Requirements Specification (SRS)

**Version:** 2.0  
**System:** Car Rental Application

**Backend:** Centralized REST API  
**Business Model:** Owner Subscription

# 1. Introduction

## 1.1 Purpose

The Car Rental Application connects Customers with Vehicle Owners and Drivers through a centralized backend. Super Admins manage verification, approvals, subscriptions and platform-level administration.

The system supports:

- Customer registration and vehicle search
- Owner registration and subscription
- Vehicle management
- Driver management
- Vehicle and Driver approval
- Booking requests
- Owner-Customer communication
- Final agreed rental price recording
- Driver assignment
- Trip execution
- Trip history
- Notifications
- Subscription management
- Role-based access control

## 1.2 Platforms

| Platform | Users | Responsibility |
|---|---|---|
| Customer Mobile App | Customer | Search vehicles, request bookings, view confirmed trips and history |
| Owner & Driver Mobile App | Owner, Driver, Owner+Driver | Manage vehicles, drivers, bookings and trips |
| Super Admin Web App | Super Admin | Approvals, subscriptions, monitoring and administration |

## 1.3 Centralized Architecture

All three applications communicate with one centralized backend and one central database.

```text
Customer Mobile App
        │
Owner & Driver Mobile App
        │
Super Admin Web App
        │
        ▼
┌─────────────────────┐
│   Central Backend   │
│     REST APIs       │
└──────────┬──────────┘
           │
           ▼
       Database
```

The backend is responsible for authentication, authorization and enforcement of business rules.

# 2. Roles

The system contains four primary roles/capabilities:

1. Customer
2. Owner
3. Driver
4. Super Admin

A single User identity may have Owner and Driver capabilities simultaneously.

Therefore a person can be:

- Owner only
- Driver capability
- Owner + Driver

Driver self-registration is not supported.

# 35. End-to-End Example

An Owner registers with Name, Mobile Number, Email and Password and completes OTP verification.

The Owner logs in and selects an active subscription.

The Owner adds a Mumbai vehicle with its specifications, pricing and RC documents. The vehicle enters pending approval. Super Admin reviews the vehicle and approves it.

The Owner creates a Driver account and provides the Driver credentials. The Driver's information and license documents are submitted for Super Admin approval. After approval, the Driver can log in and control their own availability.

A Customer selects Mumbai and searches for available vehicles. Only approved, active and non-conflicting vehicles are shown.

The Customer selects a vehicle and submits a booking request with pickup, drop, date, time, passenger and contact information.

The Owner receives the request and contacts the Customer. The Customer and Owner discuss the trip and agree on the final rental amount.

The Owner accepts the request and assigns an approved, active and available Driver. The booking becomes confirmed.

The Customer receives the Driver and Vehicle details.

If the assigned Driver later becomes unavailable, the Owner assigns another approved/active Driver and the Customer receives a notification containing the new Driver details.

If the Vehicle becomes unavailable, the Owner communicates with the Customer and agrees on the replacement arrangement. The Customer receives the updated Vehicle information.

At trip start, the Driver requests the system-generated OTP from the Customer and enters it into the application. After successful verification, the trip becomes `TRIP_STARTED`.

After completing the journey, the Driver selects End Trip and the trip becomes `TRIP_COMPLETED`.

The completed trip remains available in the appropriate Customer, Owner and Driver histories.

Customer-to-Owner rental payment is handled outside the platform. The platform stores the final agreed rental amount but does not process that rental payment.

   - Customer → Owner/Vehicle rating नाही.

   - Customer ला RC/License documents दाखवायचे नाहीत.
   - Admin documents verify करेल आणि approval/rejection देईल.
   - त्यामुळे customer-facing document access requirement ठेवण्याची गरज नाही.

   - प्रत्येक Vehicle एका Owner चीच.
   - दुसरा Owner तो vehicle वापरू/add करू शकत नाही.

15. **Driver ownership**
   - प्रत्येक Driver एका Owner शी associated.
   - दुसऱ्या Owner साठी तो Driver assign करता येणार नाही.

16. **Vehicle availability**
   Vehicle:
   - Approved
   - Active
   - Available
   
   असेल तरच customer ला booking साठी दिसेल.

   Booking झाल्यावर ते त्या booking period साठी unavailable.

   Trip complete झाल्यानंतर automatically available होण्याची eligibility येईल, **पण Owner final availability control करेल**.

   उदा.:

   `Trip Completed → Owner decides Available / Inactive`

   जर servicing चालू असेल तर Owner vehicle inactive ठेवू शकतो.

17. **Rejection + Resubmission**
   - Admin vehicle/driver reject करू शकतो.
   - Rejection reason mandatory.
   - Owner correction करून पुन्हा submit करू शकतो.

```text
       ↓
   REJECTED
       ↓
Correction
       ↓
RESUBMITTED
       ↓
PENDING_APPROVAL
       ↓
   APPROVED
```

18. **Backend**
   - Customer App
   - Owner & Driver App
   - Super Admin Web

   या तिन्हींसाठी **एकच Central Backend + एक Database**.
